# skill-creator — 把做法固化成技能

## 核心判断：这值得做成技能吗

**值得做**，当满足下面任意两条：
- 同一个流程你已经重复做过 3 次以上
- 做法有**顺序依赖**（先 A 才能 B，跳步会错）
- 有**别人会踩的坑**，且坑不明显

**不值得做**：
- 一次性任务
- 纯事实查询（该做成文档，不该做成技能）
- 只是"语气要求"（那是 system prompt 的事）

## 访谈顺序（一次问一个，不要一次抛四个问题）

1. **"什么时候该用这个技能？"** → 这决定 `description`，是**最重要的字段**
2. **"第一步做什么？"** → 从动作开始，不从背景开始
3. **"什么情况下会做错？"** → 这是技能里最值钱的部分，别人踩过的坑
4. **"做完怎么知道对了？"** → 验收标准，必须可检查
5. **"它需要哪些工具？"** → 用于 `tools:` 声明（只收敛，不授权）

## 写作规则

### description 必须写"什么时候用"

```yaml
# ✗ 错：只说了是什么
description: 一个代码审查技能

# ✓ 对：说了什么时候用
description: 当你要审查一个改动是否正确、有没有破坏现有行为时使用——
             按固定顺序检查边界条件、错误路径和权限假设。
```

`description` 是**唯一的触发依据**。写不好，技能永远不会被加载。
**必须包含**：触发场景 + 至少一个动作词（检查 / 生成 / 排查 / 对比）。

### 正文按"能执行"写

| ✗ 抽象 | ✓ 可执行 |
|---|---|
| "要仔细检查边界条件" | "检查 `0` / `空数组` / `null` / 负数 四种输入" |
| "保持代码风格一致" | "落盘前跑 `gofmt -l .`，有输出就重跑" |
| "注意权限" | "每次写文件前，先确认审计里有对应 `decision` 行" |

### 每条规则后面给一个理由或一个例子

只说"不许 X"的技能会被人（和模型）绕过。
**"不许 X，因为 Y"** 才是能站住的约束。

### 长度

- 触发 + 主流程：**30 行以内**
- 超过 150 行说明你在写文档，不是在写技能。拆开。

## 文件结构

```
skills/<slug>/SKILL.md          # 必需
skills/<slug>/examples/         # 可选：真跑过的输入输出
skills/<slug>/scripts/          # 可选：脚本，正文里用路径引用
```

```markdown
---
name: <slug>              # 小写连字符，与目录同名
description: <什么时候用 + 干什么>
---

# <标题>

## 什么时候用
## 怎么做（编号步骤）
## 坑
## 验收
```

## 最后一步

写完**立刻用一次**，把真实输出贴进 `examples/`。
没用过的技能不算写完了——只写不跑，坑是编的。
